## 合并后的执行方法

合并减少的是需要用户分别启动的任务数，原问题的修改步骤和失败验收全部保留。不要一次无测试地改遍整个仓库。

1. 建立本任务工作清单和修复分支，在下列顺序中一次处理一个问题：先回归、再实现、再验证。可为每个问题做本地提交，但无需让用户为每个问题重新开任务。
2. 复用共同的 IO/锁/时间/事务设施，避免多个问题各自实现不兼容的逻辑；公共 helper 改动后运行全部受影响测试。
3. 若达到上下文限制，在工作清单写清已完成 ID、当前提交、测试命令/结果、剩余事项和恢复入口，继续完成同一任务；不能只因任务合并而漏项。
4. 最终用 ID 对照表逐项交付；任何未完成、环境阻塞和兼容性风险单列。不要把只读验证、未知测量、损坏状态当成功。

工作顺序：CFI-04 → CFI-05。

本阶段可独立完成发布 gate，不等待真实设备缺陷全部修完；但任何真正发布仍必须等待全部资格。先修资格布尔判定，再绑定实际资产与固定依赖合同。

## CFI-04 · P1 · 发布资格校验接受 releaseEligible=false 的证据

定位：`scripts/validate-qualification-evidence.py:26–38、83–95；.github/workflows/release.yml:79`。

审计证据：已复现：schemaVersion=1、匹配 commit、releaseEligible=false、qualificationState=failed 的最小 JSON，携带 --require-assets 2 仍以 0 退出，省略迁移、Rill 和所有 assets。release 工作流使用相同命令作为资格 gate。只复现本地判定，没有触发远端发布。

### 必须实现

1. 保留诊断模式能识别并展示不可发布证据，但新增明确的发布模式，例如 --require-release-eligible；该模式必须要求字段严格为布尔 true，且状态为 automated-qualification。
2. 发布工作流显式使用严格模式；--require-assets 不能被 releaseEligible=false 的提前 return 绕过。
3. 严格模式继续检查 exact SHA、来源 workflow run、迁移、stable/preview Runtime、合同中的固定 commit/version、资产完整性。禁止把“JSON 合法”当“发布合格”。
4. 所有无效/缺失字段在创建标签、Release、上传资产前退出非零。诊断脚本的既有允许 false 测试按模式分别保留。
5. 注意 bool 是 Python int 的子类：run id 等整数值拒绝 True/False 和非正整数。不要为了过测试放宽 SHA、release state、迁移证据。

### 验收测试

- 将 evidence/noneligible.json 输入发布模式，必须非零且没有任何发布动作；诊断模式可成功展示“不合格”。
- false、字符串 true、null、缺字段、failed 状态、错误 commit、缺 migration/Rill/assets 各自拒绝。
- 完整真实合格 fixture 接受；只改一个强制 PASS 为 FAIL 就拒绝。
- workflow 测试证明资格失败时 tag/create/upload/API promotion 均不调用，不能仅 grep 参数名。

## CFI-05 · P1 · 资格资产摘要没有绑定实际上传包

定位：`scripts/validate-qualification-evidence.py:75–80；tests/release-asset-contract.sh；release.yml:134–135 与上传步骤`。

审计证据：静态确认：资格 validator 只检查 assetFiles 长度和 SHA 字符串格式；release-asset-contract 检查的是 release 目录内刚生成的 sha256sums，不比较 qualification.json 的摘要和文件名。两个各自自洽但内容不同的包集合可分别通过，exact source SHA 并不等价于 exact build bytes。

### 必须实现

1. 发布前把 qualification.json 的 assetFiles 按规范化相对 basename 建立唯一映射，要求恰好一个本版本 base ipk 和 apk，无重复、路径穿越、未知包和 addon 混入。
2. 对待上传目录计算真实字节 SHA-256、大小及包版本/架构元数据，逐一与本 run 资格证据匹配；生成上传 checksum 时只使用通过此绑定的资产。
3. 若资格构建和发布构建本来不是同一产物，改为上传资格构建资产；或明确加入可验证的可重复构建比较，不能简单改资格中的 hash 去适配第二次构建。
4. 迁移 sourceSHA、Rill package/runtime commits 必须比对 contracts/rill-runtime.json 固定值，而非仅形状合法。若证据另有签名/运行标识继续保留。
5. 把完整绑定写成可独立调用的函数/CLI，使 workflow 和测试共用。资格 manifest 自身要来自该 exact run，不接受目录内任意同名 JSON。

### 验收测试

- 制作两个大小/版本相同、字节不同的 ipk/apk fixture；manifest 对 A，release/checksums 对 B：必须拒绝。
- 改一个字节、交换 hash、重复名、只有 hash 没 name、绝对路径、../、额外资产、错误 package release/version/architecture 均拒绝。
- 真实同 run 原始产物接受，生成 checksum 为相对路径且可以 sha256sum -c。
- 固定合同中的任一 commit/run/digest 不匹配时拒绝；不能仅检查 SHA 正则。
