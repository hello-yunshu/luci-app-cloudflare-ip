# RPC failure and permission contract

Synchronous backend RPC methods accept exactly one JSON object. A nonzero backend exit forces success=false and retains its exit code in rc, alongside existing diagnostic fields and the root error. Empty, malformed, non-object or multiple-object output becomes a failure object. Successful existing status objects may omit success; their fields remain compatible. speedtest-status combines one status object with one normalized log_data object, so a log failure remains visible without duplicating the top-level response.

Service start/stop/restart must stop before invoking the lifecycle action if UCI set, UCI commit or required init enable fails. Errors identify the failed prerequisite and its exit code. This does not promise rollback of pending or already committed UCI changes after a later failure. Shared writer locks are released on these reported failures.

refresh-env writes the environment cache and therefore requires write permission. The source ACL classifies every declared RPC method exactly once; mutation methods are not in the read class. Overview treats a failed/missing refresh response as an error and keeps the last displayed environment state. The cached detection is updated only on a successful response.

The host matrix executes the production shell dispatcher with controlled backend/UCI/init/parser fixtures. Its ACL checks inspect source policy, and its UI checks execute the production handler in an isolated module DOM. Native authenticated read-only/write rpcd sessions, real UCI/procd event propagation and full browser/responsive/keyboard acceptance require separate evidence; these fixtures do not close those gates.

## Asynchronous run startup

The run method uses a private anonymous pipe for one startup response. The actual backend validates committed configuration twice and acquires the existing shared writer lock before acknowledging. The response contains acknowledged, accepted, running, the actual owner PID, a requestId and observedAt. This is evidence of entering the run at that observation, not successful measurement or application. Later progress and outcomes remain separate status observations.

The RPC waits at most eight seconds for the startup message (the internal test override accepts 1–8) and caps its reply read. Exactly one object with the matching requestId and required startup fields is accepted. Missing backends and pre-ack backend errors return failure details. A missing/malformed/unmatched acknowledgement or timeout returns unconfirmed=true with accepted/running=null: this cannot prove that the task never began, so check status before retrying. If the reader has already disappeared before the backend attempts its acknowledgement, the broken-pipe failure stops it before context/transaction mutation and releases its acquired lock.

The pipe is separate from task stdout. The detached worker closes inherited stdin/stderr so rpcd does not wait for the entire background task to finish. No temporary FIFO tool or persistent job payload is introduced. The source-only shell mode is internal and is not a declared ubus method. Host sh and dash tests execute the actual RPC and backend entry/lock ordering with isolated configuration/context callbacks; native rpcd/BusyBox/procd and the complete storage/concurrency failure matrix still require separate qualification.

## Early failure and observation identity

Startup acknowledgement includes the runId allocated before context setup. Status serialization includes the same runId and the RPC requestId (null for non-RPC entries). Overview now matches both runId and requestId before its post-start reload, using a bounded, navigation-cancellable status poll. A matching terminal failure is displayed through the normal status page; observing a task is not a success claim. Missing status or a timeout reports an observation problem and asks the user to inspect status/logs before retrying. Other clients must likewise match runId before treating a status response as the outcome of the acknowledged task; a previous or foreign record is not that task's completion.

The prior status is fingerprinted under the shared writer lock without replacing it before the reuse decision. This preserves the existing successful-IP reuse gate. Once the run entry is acknowledged, early context errors, raw exits and TERM can publish an inactive failure record even if the first normal progress record was never written. Cleanup may update its own run-tagged record or an unchanged pre-start cache, and requires retained writer ownership. It preserves already recorded specific terminal errors and adds any later recovery error. Foreign edits, symlinks and lost writer ownership are preserved and logged instead of being replaced by an old task.

The host matrix covers both provider modes, initial missing status, active/completed/error records, root/recovery errors, foreign edits/links, snapshot failure and lost ownership. Configuration/context/health are controlled fixtures; hashes prove fixture user data, configuration, backup and history preservation. Terminal write failure cannot be repaired by a read-only status cache; the publication failure is logged and storage qualification remains OPEN. These checks do not prove universal filesystem CAS, complete stale-lock recovery, native rpcd/procd behavior or the Overview/browser observation-matching flow.
