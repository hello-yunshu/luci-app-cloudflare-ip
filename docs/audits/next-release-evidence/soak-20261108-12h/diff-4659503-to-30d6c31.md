## So: is the intermediate window substitutable?

- **Backend behaviour:** the object installed during the `4659503` window runs
  exactly the same init scripts, engine and rpcd as `30d6c31`. A soak harness
  that only scores backend stability (`ubus cf_ip status`, mihomo process
  count, cron entries, error counter, memory) therefore measures the same code
  before and after.
- **Shipped artifact:** it is *not* the same artifact. The 4 frontend files
  (CSS + `overview`/`intelligence`/`settings` views) and the 3 translation
  catalogs change the bytes that a user installs. The `4659503` window
  contains no observation of the `30d6c31` frontend, and the acceptance
  object for a release must be the exact artifact, not a near-relative.
- **Therefore:** the `4659503` window is recorded as **intermediate evidence,
  not final acceptance**, and does **not** get upgraded to a pass simply
  because it ran a full 12 h. A full window on `30d6c31` is mandatory.

The 42-file diff contains no change to any `root/` runtime file, so the
intermediate window also cannot be rejected on the grounds that backend code
moved underneath it; the limitation is artifact identity, not backend drift.
